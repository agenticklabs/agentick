# MCP 2026-07-28 — the era migration decision

**Status: DECISION DOC** — 2026-07-30, from the spec-delta recon (fetched
evidence; URLs inline). Companion to `mcp-parity.md`, which audited against
`2025-11-25 + draft` and is accurate for that era. This doc covers what the
NEW era changes and the decisions it forces. Nothing here is built.

## The situation in three sentences

`2026-07-28` is the current official MCP revision and it is a **protocol
rewrite**, not a point release: stateless (no `initialize`, no sessions), a
mandatory `server/discover`, `subscriptions/listen` replacing the GET stream
and resource subscribe/unsubscribe, and — deepest — **MRTR** replacing every
server-initiated request (`elicitation/create`, `sampling/createMessage`,
`roots/list`) with `resultType: "input_required"` continuations carrying a
signed, client-echoed `requestState` token. The official TypeScript SDK
answered with a **package split already GA at 2.0.0**
(`@modelcontextprotocol/server` / `client` / `node` / `express` / `fastify` /
`hono`), whose legacy shim serves BOTH eras from one handler implementation —
the monolith `@modelcontextprotocol/sdk` tops out at `2025-11-25` forever
(verified: 1.30.0's constants are byte-identical to 1.29.0's). Our repo
currently **advertises the new era in its labels and speaks the old one in
substance** — `McpSpecEra` lists `"2026-07-28"` and the passthrough codec
claims it (commit `0cbe88e3`), while the SDK underneath cannot utter it and
`package.json` / README / `mcp-parity.md` still say `2025-11-25 + draft`.

**Explicitly unchanged:** pagination (`cursor`/`nextCursor`), icons,
**completions** (our P1–P3 vertical is era-safe), elicitation URL mode
(official, retained, minus the correlation fields), the form-mode flat-schema
rule (our validator stays right). MCP Apps is an extension
(`io.modelcontextprotocol/ui`), not core.

## Decisions this forces (in order)

1. **Reconcile the three contradicting version claims** (cheap, first):
   `packages/mcp/package.json` description + `packages/mcp/README.md` say
   `draft / 2025-11-25`; the code's era enum claims `2026-07-28`; the truth is
   "speaks 2025-11-25; labels reserved for 2026-07-28". Say the truth in all
   three places until the migration lands.
2. **SDK v2 migration = its own ADR.** Swaps one dependency for up to six
   across **121 import sites**; in exchange the legacy shim gives us
   `server/discover`, statelessness, header rules, AND both-era service from
   one implementation — including auto-converting MRTR `inputRequired(...)`
   returns into real server→client requests on old-era connections, so the
   elicitation projection is written ONCE. Entry points: `createMcpHandler`
   (`legacy: 'stateless' | 'reject'`), `serveStdio`, `new Client(info, {
versionNegotiation: { mode: 'auto' } })`.
3. **Design the MRTR / `requestState` seam BEFORE building.** A signed,
   replay-bounded, client-echoed continuation token (spec: MUST treat as
   attacker-controlled; MUST protect integrity — HMAC/AEAD; SHOULD bind
   principal + TTL + originating request) is a primitive agentick does not
   have anywhere. It intersects our elicitation harness (an `elicit()` that
   suspends into a token instead of awaiting a push), credentials (key
   custody for the MAC), and the crossing ctx. This is where our architecture
   has an opinion; doc-first.
4. **Era-codec honesty.** `selectCodec` returns one passthrough for every
   era. Post-migration, `2025-11-25` becomes the era needing a REAL codec —
   it is no longer "near-canonical", it is a different protocol.

## What today's in-flight work keeps

Defect fixes #250–#255 are era-independent or old-era-valid (the installed
base — every deployed MCP client today — speaks 2025-11-25 or older; serving
it well is not legacy work, it is the product). The opt-in HTTP `eventStore`
is old-era-only by spec and should say so in its doc. Native-wire work
(pagination envelope, `fromCursor`, `session/abort`, honest `initialize`) is
agentick's own wire and untouched by any of this.
