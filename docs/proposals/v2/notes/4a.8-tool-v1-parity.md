# 4a.8 — Tool executor v1 parity sweep

**Status:** closed (audit-only). 2026-05-18.

## Findings

Audited v1's tool test corpus (~50 cases across
`packages/core/src/tool/__tests__/*.spec.*` and
`packages/core/src/engine/tool-executor-sandbox.spec.ts`) against v2's
65 tool-executor tests. **There's nothing to port — the gaps between
v1 and v2 are feature gaps, not test gaps.**

### Substrate-level behavior — fully covered in v2

These v1 behaviors all have v2 equivalents tested:

| Behavior | v1 source | v2 coverage |
|---|---|---|
| Register a tool | `tool.test.ts` | `registry.spec.ts` (10 cases) |
| Dispatch happy path | `tool-component.spec.tsx` | `harness.spec.ts` (15 cases) |
| Validation failures | `tool.test.ts` | `validator.spec.ts` (6 cases) + harness error-path cases |
| Abort in-flight | `tool-component.spec.tsx` | `harness.spec.ts` abort section |
| Timeout handling | `tool.test.ts` | `harness.spec.ts` (timeout case) |
| Confirmation flow | `tool-confirmation.spec.tsx` | `confirmation.spec.ts` (6 cases) |
| Handler error → tagged result | inline in component tests | `harness.spec.ts` ToolHandlerError case |
| Middleware composition | n/a in v1 (executor middleware) | `middleware-and-hooks.spec.ts` (6 cases) |
| Channel-based progress | inline in tool-confirmation | covered via `ctx.emit` + `LocalChannelPublisher` |

### v1-only features — explicitly *not* carried into v2 yet

These are feature gaps, not test gaps. They land when v2 builds the
user-facing tool authoring surface (likely a `@agentick/tool` factory
package).

| v1 feature | What it does | v2 status |
|---|---|---|
| `createTool({...})` factory | Typed tool authoring with `input`, `handler`, optional `render`/`use` | **Not built.** v2 uses `InMemoryHandlerResolver.register(handlerRef, handler)` as the low-level surface today. |
| Tool `render()` function | Render-time output that becomes part of the model context | **Not built.** v2's declarations pipeline is rendered-tree-based; tool render is a different model. |
| JSX `<Tool>` prop overrides | `<Tool description="..." requiresConfirmation />` at JSX render time | **Not built.** v2's `ToolDeclaration` is immutable in `RenderedTree`. |
| `use()` hook on tools | Render-time context injection (sandbox, services, etc.) into handler `deps` | **Not built.** Planned with the `createTool` factory. |
| Tool source merging priority | app > session > JSX > execution | **Not built.** v2 has one shared `HandlerResolver` per app today. |
| Sandbox access recovery flow | `SandboxAccessError` → confirmation → retry → cleanup | **Not built at substrate level.** Higher-layer concern; would compose on top of the confirmation flow we already have. |

### Behavior intentionally simplified

| v1 | v2 |
|---|---|
| Tool result with `succeeded: false` carries denial info | Same shape preserved (matches v1 for denial; v2 only diverges on terminal envelope where v1 uses `succeeded` flag, v2 layers the lifecycle envelope on top of the same result shape) |
| Multiple tool exposures (`model` / `user` / `all`) | Replaced with explicit exposure array `["model", "dispatch", "runtime"]` |
| ToolClass static metadata + per-instance overrides | Single `ToolDeclaration` shape with `annotations` |

## Conclusion

Substrate parity is achieved. The user-surface feature gap (`createTool`
+ `use()` + JSX overrides) is the next user-visible tool work — it's
scoped as a separate beat (`@agentick/tool` package), not a backfill of
the executor harness. No v1 tests to port.

**Closing 4a.8 as documentation-only.**
